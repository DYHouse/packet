# CashParty 红包游戏系统产品需求文档（PRD）

## 1. 产品概述

### 1.1 产品名称
CashParty - 多人在线红包抢夺游戏系统

### 1.2 产品定位
CashParty是一款基于红包玩法的多人在线社交游戏，玩家可以在虚拟房间中进行红包发送和抢夺，通过策略和运气获得游戏收益。系统支持多种特殊奖励机制，提供公平、有趣的游戏体验。

### 1.3 目标用户
- 喜欢社交游戏的年轻用户群体
- 寻求休闲娱乐的移动端用户
- 对红包玩法感兴趣的游戏玩家

## 2. 核心业务流程

### 2.1 游戏房间生命周期

#### 2.1.1 房间状态
系统支持以下房间状态：
- **空闲状态**：房间刚创建，等待玩家加入
- **等待状态**：玩家已入座，等待准备开始游戏
- **游戏中状态**：游戏正在进行
- **中断状态**：游戏因玩家离开等原因中断，等待替补

#### 2.1.2 房间配置
- 房间类型：根据入场费用区分不同等级房间
- 最大玩家数：每个房间可容纳的玩家数量上限
- 最大回合数：每局游戏进行的轮次
- 最大观众数：允许旁观的人数上限

### 2.2 玩家角色与状态

#### 2.2.1 玩家角色
- **观众**：进入房间但未选择座位的用户，可观看游戏进程
- **玩家**：已选择座位并参与游戏的用户

#### 2.2.2 玩家状态
- **在线**：玩家正常在线
- **离线**：玩家断线但未超时
- **准备**：玩家已准备开始游戏
- **游戏中**：玩家正在参与游戏

### 2.3 游戏流程详解

#### 2.3.1 入场阶段
1. **加入房间**
   - 用户通过房间号或自动匹配进入房间
   - 系统验证用户余额是否符合房间要求
   - 用户默认以观众身份进入

2. **选择座位**
   - 观众点击空座位成为玩家
   - 系统分配座位号
   - 设置选座超时时间（默认30秒）

3. **取消座位**
   - 游戏未开始前，玩家可取消座位变回观众
   - 游戏进行中不可取消座位

4. **准备游戏**
   - 玩家点击准备按钮
   - 清除选座超时计时器
   - 系统检测是否满足开始条件

#### 2.3.2 倒计时阶段
1. **开始条件**
   - 所有已入座玩家都已准备
   - 玩家数量达到最低要求（至少3人）

2. **倒计时流程**
   - 系统开始3秒倒计时
   - 实时推送倒计时状态给所有用户
   - 倒计时结束自动开始游戏

3. **异常处理**
   - 倒计时期间有玩家离开，取消倒计时
   - 房间状态变更，终止倒计时

#### 2.3.3 游戏进行阶段

**第一轮：系统发红包**
1. 游戏开始，系统自动发送第一个红包
2. 红包金额 = 房间费用 - 手续费
3. 红包数量 = 房间最大玩家数
4. 设置抢红包超时时间（默认10秒）

**后续轮次：玩家发红包**
1. 上一轮抢到最小金额的玩家成为下一轮发红包者
2. 发红包者账户扣除房间费用
3. 系统生成随机金额的红包
4. 其他玩家抢红包

**抢红包机制**
1. 每个玩家每轮只能抢一个红包
2. 红包金额随机分配
3. 抢到红包后实时推送结果
4. 所有红包被抢完或超时后进入结算

**超时处理**
- 抢红包超时：系统自动分配剩余红包给未抢的玩家
- 发红包超时：系统强制代发红包并记录惩罚

#### 2.3.4 结算阶段

**单轮结算**
1. 统计本轮所有玩家的抢红包金额
2. 找出最小金额获得者（下一轮发红包者）
3. 推送本轮结果给所有用户
4. 判断是否达到最大轮次

**整局结算**
1. 统计所有玩家的总发送金额、总抢到金额、总收益
2. 按收益排名
3. 推送最终结果
4. 玩家转换为观众状态
5. 房间状态重置为等待状态

### 2.4 特殊奖励机制

#### 2.4.1 顺子奖励
- **触发条件**：红包金额的整数部分形成连续递增序列
- **奖励金额**：等于房间费用
- **触发概率**：默认8%

#### 2.4.2 豹子奖励
- **触发条件**：所有红包金额完全相同
- **奖励金额**：房间费用 × 10
- **触发概率**：默认0.2%

#### 2.4.3 彩池奖励
- **彩池机制**：每局游戏从红包总额中抽取一定比例（默认1%）注入彩池
- **触发条件**：随机触发（默认概率0.05%）
- **奖励金额**：当前彩池全部金额
- **彩池重置**：触发后彩池重置为初始值（默认100,000）

#### 2.4.4 RTP控制机制
- **目标RTP**：95%（玩家平均回报率）
- **动态调整**：当实际RTP偏离目标值超过阈值时，自动调整特殊奖励概率
- **调整策略**：
  - 实际RTP过高：降低特殊奖励概率
  - 实际RTP过低：提高特殊奖励概率

## 3. 惩罚机制

### 3.1 惩罚类型

#### 3.1.1 发红包超时惩罚
- **触发场景**：轮到玩家发红包时，玩家未在规定时间内操作
- **惩罚措施**：
  - 第一次：系统代发红包，记录惩罚次数
  - 第二次：踢出房间，扣除房间费用作为惩罚金
- **惩罚金分配**：平均分配给房间内其他玩家

#### 3.1.2 游戏中离开惩罚
- **触发场景**：玩家在游戏进行中主动离开房间
- **惩罚措施**：扣除房间费用作为惩罚金
- **惩罚金分配**：平均分配给房间内其他玩家

#### 3.1.3 断线超时惩罚
- **触发场景**：玩家断线超过规定时间（默认60秒）
- **惩罚措施**：踢出房间，如游戏进行中则扣除惩罚金
- **惩罚金分配**：平均分配给房间内其他玩家

### 3.2 惩罚记录
- 系统记录每个玩家在当前房间的惩罚次数
- 游戏结束后清空惩罚记录
- 达到惩罚上限自动踢出房间

## 4. 房间替补机制

### 4.1 中断状态
当玩家因惩罚被踢出时：
1. 房间状态变更为"中断"
2. 空出被踢玩家的座位
3. 设置替补等待时间（默认30秒）

### 4.2 补位流程
1. 观众可点击空座位补位
2. 补位玩家继承被踢玩家的游戏数据
3. 补位完成后游戏继续

### 4.3 补位超时
- 补位等待时间内无人补位
- 系统分配惩罚金给剩余玩家
- 游戏结束，房间重置

## 5. 断线重连机制

### 5.1 断线检测
- 系统通过心跳检测玩家连接状态
- 心跳超时判定为断线

### 5.2 重连流程
1. 玩家断线后，系统保留玩家状态
2. 玩家重新连接，验证身份
3. 恢复玩家在房间中的状态
4. 推送当前房间状态给玩家

### 5.3 断线超时
- 断线超过规定时间未重连
- 系统自动踢出玩家
- 如游戏进行中，触发惩罚机制

## 6. 消息推送机制

### 6.1 实时推送类型

#### 6.1.1 房间状态推送
- 房间信息变更
- 玩家加入/离开
- 座位选择/取消
- 玩家准备状态

#### 6.1.2 游戏状态推送
- 游戏开始
- 倒计时
- 回合开始
- 红包被抢
- 回合结束
- 游戏结束

#### 6.1.3 系统消息推送
- 踢出通知
- 惩罚通知
- 自动分配通知
- 游戏中断通知

### 6.2 推送策略
- 房间内广播：推送给房间内所有用户
- 排除推送：推送给房间内除指定用户外的所有用户
- 定向推送：推送给指定用户

## 7. 平台对接需求

### 7.1 平台接口规范

#### 7.1.1 接口类型
系统需要与平台系统对接以下接口：

**账户管理接口**
- **扣款接口**：`POST /api/account/deduct`
  - 功能：从玩家账户扣除指定金额
  - 参数：用户ID、金额、订单号、备注、追踪ID
  - 返回：扣款前余额、扣款后余额、交易流水号
  
- **加款接口**：`POST /api/account/credit`
  - 功能：向玩家账户增加指定金额
  - 参数：用户ID、金额、订单号、备注、追踪ID
  - 返回：加款前余额、加款后余额、交易流水号

- **余额查询接口**：`GET /api/account/balance`
  - 功能：查询玩家账户余额
  - 参数：用户ID
  - 返回：可用余额、冻结金额、总余额

#### 7.1.2 接口安全机制
- **API Key认证**：每个请求携带API Key和API Secret
- **时间戳验证**：请求头包含时间戳，防止重放攻击
- **签名验证**：对请求参数进行签名验证
- **HTTPS加密**：所有接口使用HTTPS协议

#### 7.1.3 接口超时与重试
- **超时设置**：默认10秒超时
- **重试策略**：失败后最多重试3次，间隔1秒
- **幂等性保障**：通过订单号保证接口幂等性

### 7.2 玩家基本信息管理

#### 7.2.1 用户信息获取
当玩家首次连接时，系统需要获取并保存玩家基本信息：
- **用户ID**：平台唯一标识
- **昵称**：玩家显示名称
- **头像**：玩家头像URL
- **设备ID**：玩家设备标识
- **IP地址**：玩家连接IP

#### 7.2.2 用户信息存储
- **数据库存储**：持久化用户基本信息到MySQL
- **缓存机制**：Redis缓存用户信息30分钟
- **更新策略**：每次连接时检查并更新用户信息

#### 7.2.3 用户信息使用场景
- 进入房间时显示玩家昵称和头像
- 游戏过程中推送玩家信息
- 结算记录中保存玩家信息快照

### 7.3 账户管理流程

#### 7.3.1 余额检查流程
**触发时机**：
- 玩家选择座位准备成为玩家时
- 玩家自动匹配房间时

**检查流程**：
1. 调用平台余额查询接口
2. 验证余额是否大于等于房间费用
3. 余额不足时拒绝入座或匹配
4. 余额充足时允许继续操作

#### 7.3.2 扣款流程
**触发时机**：
- 玩家发送红包时
- 玩家因惩罚被扣款时

**扣款流程**：
1. 生成唯一订单号（格式：`deduct_{roundID}_{userID}`）
2. 调用平台扣款接口
3. 记录扣款前后余额
4. 保存扣款流水记录
5. 返回扣款结果

**扣款失败处理**：
- 余额不足：拒绝操作，提示用户充值
- 接口超时：重试3次，失败后记录异常日志
- 系统异常：记录错误，通知管理员

#### 7.3.3 加款流程
**触发时机**：
- 玩家抢到红包后结算时
- 玩家获得特殊奖励时
- 惩罚金分配时

**加款流程**：
1. 计算加款金额（抢红包金额 + 奖励金额）
2. 生成唯一订单号（格式：`credit_{roundID}_{userID}`）
3. 调用平台加款接口
4. 记录加款前后余额
5. 保存加款流水记录
6. 返回加款结果

**加款失败处理**：
- 接口超时：重试3次，记录失败日志
- 系统异常：记录错误，后续人工处理
- 保证最终一致性：通过补偿机制确保玩家获得应得金额

## 8. 结算系统

### 8.1 手续费机制

#### 8.1.1 手续费计算
- **费率**：默认5%（可配置）
- **计算公式**：手续费 = 房间费用 × 手续费率
- **实际红包金额**：房间费用 - 手续费

#### 8.1.2 手续费记录
**记录内容**：
- 房间ID、轮次ID
- 房间类型、房间费用
- 手续费金额、实际红包总额
- 创建时间

**记录时机**：
- 每次发红包时记录手续费明细
- 保存到`commission_record`表

#### 8.1.3 手续费统计
- 按房间类型统计手续费总额
- 按时间段统计手续费收入
- 用于财务报表和收益分析

### 8.2 发红包扣款流程

#### 8.2.1 扣款时机
- **玩家发红包**：轮到玩家发红包时，立即扣款
- **系统代发**：玩家超时或被踢出时，系统代发红包（不扣款）
- **强制发红包**：玩家超时惩罚后，系统强制代发（记录惩罚）

#### 8.2.2 扣款详细流程
1. **验证玩家状态**
   - 检查玩家是否在线
   - 检查玩家是否在游戏中
   - 检查是否轮到该玩家发红包

2. **计算扣款金额**
   - 扣款金额 = 房间费用
   - 计算手续费 = 房间费用 × 5%
   - 计算实际红包金额 = 房间费用 - 手续费

3. **调用平台扣款接口**
   - 生成订单号：`deduct_{roundID}_{userID}`
   - 备注信息：`CASH_PARTY发红包,房间ID:{roomID},局ID:{roundID}`
   - 调用扣款接口
   - 获取扣款后余额

4. **记录扣款流水**
   - 保存扣款记录到数据库
   - 记录扣款前后余额
   - 记录交易流水号

5. **生成红包**
   - 调用红包生成算法
   - 根据实际红包金额生成多个随机金额
   - 保存红包信息到Redis

#### 8.2.3 扣款失败处理
- **余额不足**：
  - 拒绝发红包操作
  - 踢出玩家
  - 系统代发红包
  
- **接口异常**：
  - 重试3次
  - 失败后记录异常
  - 暂停游戏，等待人工处理

### 8.3 每轮结算流程

#### 8.3.1 结算触发时机
- 所有红包被抢完
- 抢红包超时（自动分配剩余红包）
- 游戏异常中断

#### 8.3.2 结算详细流程

**第一步：收集结算数据**
1. 获取本轮所有红包信息
2. 统计每个玩家抢到的红包金额
3. 找出最小金额获得者（下一轮发红包者）
4. 检查是否触发特殊奖励

**第二步：计算特殊奖励**
1. 根据红包金额分布判断奖励类型
   - 顺子奖励：红包金额整数部分连续递增
   - 豹子奖励：所有红包金额相同
   - 彩池奖励：随机触发
2. 计算奖励总金额
3. 平均分配给所有参与本轮的玩家

**第三步：幂等性检查**
1. 检查该轮次是否已结算
2. 查询`settlement_record`表是否存在该轮次记录
3. 如已结算，跳过本次结算
4. 使用分布式锁防止并发结算

**第四步：调用平台加款接口**
对每个参与本轮的玩家：
1. 计算加款金额 = 抢红包金额 + 奖励金额
2. 生成订单号：`credit_{roundID}_{userID}`
3. 调用平台加款接口
4. 记录加款前后余额
5. 失败时重试3次

**第五步：保存结算记录**
1. 保存轮次结算记录到`settlement_record`表
   - 追踪ID、房间ID、轮次ID、轮次号
   - 总金额、手续费、奖励类型、奖励金额
   - 最小金额玩家ID、玩家数量、结算状态
   
2. 保存玩家结算明细到`player_settlement_record`表
   - 玩家ID、抢红包金额、是否最小
   - 奖励类型、奖励金额、收益金额
   - 加款后余额、交易流水号

**第六步：推送结算结果**
1. 推送本轮结算结果给所有玩家
2. 包含每个玩家的抢红包金额、奖励金额
3. 标识下一轮发红包者
4. 判断是否游戏结束

#### 8.3.3 结算异常处理
- **加款失败**：
  - 记录失败玩家信息
  - 后续通过补偿机制补发
  - 通知管理员人工处理
  
- **数据库异常**：
  - 回滚事务
  - 重试结算流程
  - 记录异常日志

- **并发冲突**：
  - 使用分布式锁保证同一轮次只结算一次
  - 通过幂等性检查避免重复结算

#### 8.3.4 结算数据统计
**实时统计**：
- 每轮游戏的总投注额
- 每轮游戏的总派奖额
- 每轮游戏的手续费收入
- 特殊奖励触发次数

**历史统计**：
- 按时间段统计游戏数据
- 按房间类型统计收益
- 玩家收益排行榜
- RTP实时监控

### 8.4 整局结算流程

#### 8.4.1 整局结算触发
- 达到最大轮次
- 游戏异常终止
- 玩家全部离开

#### 8.4.2 整局结算内容
1. **统计每个玩家的总数据**
   - 总发送金额
   - 总抢到金额
   - 总奖励金额
   - 总收益 = 总抢到 + 总奖励 - 总发送

2. **生成排名**
   - 按总收益降序排名
   - 记录每个玩家的排名

3. **推送最终结果**
   - 推送每个玩家的最终收益
   - 推送排名列表
   - 推送游戏结束通知

4. **保存整局记录**
   - 保存游戏会话记录
   - 保存每个玩家的游戏数据
   - 更新玩家统计数据

#### 8.4.3 房间状态重置
1. 所有玩家转换为观众状态
2. 清空玩家的游戏数据
3. 房间状态重置为等待状态
4. 清空惩罚记录
5. 准备下一局游戏

### 8.5 结算记录管理

#### 8.5.1 记录类型
- **手续费记录**：`commission_record`
- **轮次结算记录**：`settlement_record`
- **玩家结算明细**：`player_settlement_record`
- **游戏会话记录**：`game_sessions`
- **玩家游戏记录**：`session_players`

#### 8.5.2 记录查询
- 按轮次ID查询结算详情
- 按追踪ID查询结算流程
- 按玩家ID查询历史收益
- 按时间段统计结算数据

#### 8.5.3 记录状态
- **处理中**：结算正在进行
- **成功**：结算完成
- **失败**：结算异常，需人工处理

### 8.6 结算补偿机制

#### 8.6.1 补偿场景
- 加款接口调用失败
- 数据库保存失败
- 系统异常导致结算中断

#### 8.6.2 补偿流程
1. 定时扫描失败的结算记录
2. 重新执行结算流程
3. 更新结算状态
4. 通知相关人员

#### 8.6.3 人工处理
- 提供管理后台查询失败记录
- 支持手动触发补偿
- 记录人工处理日志
